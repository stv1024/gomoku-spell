# 技能五子棋 — 技术方案设计理据

本文档记录了这套技术方案的完整推导过程。目的是让开发人员理解每一个设计决策背后的"为什么"，而不只是"是什么"。

---

## 一、项目的根本目标

这个项目表面上是一个五子棋游戏，但它真正想验证的是一件事：**能不能让 AI 在游戏运行时动态生成游戏机制、游戏逻辑、游戏代码？**

具体来说：玩家输入一个任意的四字成语，AI 实时把这个成语解读为一个五子棋技能，生成可执行的代码，立刻在棋盘上生效。这意味着游戏的技能不是开发阶段预先写好的，而是在玩的过程中由 AI 现场创造的。

这个目标决定了整个技术架构的核心矛盾：**我们不知道 AI 会生成什么样的技能，但我们必须保证它生成的任何技能都能在引擎上正确运行。**

---

## 二、核心矛盾：沙盒的边界问题

### 2.1 问题的发现

在脑暴阶段，我们列举了大量成语可能对应的技能效果。比如：

- "偷梁换柱"→ 把对手的一颗棋子变成自己的
- "暗度陈仓"→ 落一颗隐藏棋子，对手看不见
- "乾坤大挪移"→ 旋转棋盘上一个区域的所有棋子
- "以逸待劳"→ 跳过本回合，下回合连续行动三次
- "雾里看花"→ 接下来几回合对手看不到你的落子位置

我们很快发现一个根本性问题：**AI 生成的代码只能操作引擎暴露的接口。如果引擎没有"隐藏棋子"的概念，"暗度陈仓"就做不了；如果引擎没有"跳过回合"的能力，"以逸待劳"也做不了。**

换句话说，AI 生成的内容一定运行在一个沙盒环境内，而很难超出这个沙盒。引擎的能力边界就是技能的表达力天花板。

### 2.2 问题的本质

这不是一个 bug，而是"运行时生成逻辑"这件事最根本的张力。生成的内容不是真正的"涌现"，而是在预设表达能力范围内的"组合"。

所以我们面对的核心设计问题是：**怎样设计沙盒，让它的边界足够宽，宽到 AI 能生成我们没有预见过的技能？**

---

## 三、三种架构方案的比较

我们评估了三种可能的技术路线：

### 方案 A：纯配置型

预定义二三十个参数字段（如 type、target、range、count、duration），AI 只需要填参数。

优点是最安全最可控，引擎只需要做参数解释器。缺点是天花板最低——技能本质上只是参数的排列组合，玩几轮就会觉得大同小异。更重要的是，一旦想做稍微复杂的逻辑（比如"金蝉脱壳"需要在棋子被移除时触发，找到相邻空位，把棋子挪过去），纯配置根本无法表达条件判断和流程逻辑。

**结论：放弃。表达力不够。**

### 方案 B：配置 + 代码混合型

大部分技能靠配置组合生成，但允许 AI 生成一小段代码来处理特殊逻辑。

可行，但会导致系统复杂度很高——需要同时维护配置解释器和代码执行器，两套体系的交互边界也很难定义清楚。

**结论：不选。复杂度与收益不匹配。**

### 方案 C：纯代码生成型

AI 直接生成一个技能函数，入参是 BoardAPI 对象，函数体里调用 API 方法来操作棋盘。引擎只管执行。

这意味着技能的表达力天花板不再是"有哪些预设参数"，而是"BoardAPI 暴露了哪些操作"。只要 API 足够丰富，AI 可以写出任意复杂的逻辑——条件判断、循环、多步骤交互、延迟触发等等都能做。

**结论：选这个。天花板最高，最符合"运行时生成游戏机制"的实验目标。**

这个选择直接决定了后续所有设计：我们需要的不是一个"技能配置 schema"，而是一套"棋盘操作 API"。

## 四、数据结构为什么设计成开放式

### 4.1 最初的想法：预定义属性

确定了方案 C 之后，下一个问题是棋盘数据结构怎么设计。

最直觉的做法是预定义一组属性。比如每个格子有 `isBlocked: boolean`，每个棋子有 `isHidden: boolean`、`isFrozen: boolean`。这样引擎和渲染层都能明确知道怎么处理每种状态。

### 4.2 发现预定义属性行不通

但我们很快意识到这条路走不通。原因是：

**你永远列不完。** 今天你预留了 `isHidden`，明天 AI 想做一个"棋子会随回合数增长变强"的技能，你需要一个 `power` 属性。后天它想做"这颗棋子被吃掉后会爆炸影响周围"，你又需要 `onRemoved` 回调。每一个新属性都意味着要改数据结构、改引擎逻辑、改渲染层。

这直接违背了项目的核心目标——我们就是因为不知道 AI 会生成什么才做这个实验的。如果每个新技能都需要改代码，那就不是"运行时生成"了，而是"开发时预埋"。

### 4.3 解决方案：tags + props + triggers

所以我们把格子和棋子的数据结构设计成完全开放的：

```
stone: {
  owner: "black" | "white",      // 唯一的固定字段
  visibleAs: "black" | "white" | null,  // 唯一的固定字段
  tags: Set<string>,              // 无 schema，AI 自由写入
  props: Map<string, any>,        // 无 schema，AI 自由写入
  triggers: Map<string, Function> // 无 schema，AI 自由注册
}
```

这个设计的关键在于：**引擎不需要认识任何具体的 tag 或 prop**。`"hidden"`、`"frozen"`、`"radioactive"`、`"weighted"` 对引擎来说都一样——就是 Set 里的一个字符串，Map 里的一个键值对。

具体的语义完全由 AI 生成的技能代码自己定义。"暗度陈仓"的代码往棋子上加一个 `"hidden"` tag，同时注册一个延迟效果在 3 回合后移除这个 tag——引擎全程只是忠实地存储数据、在正确的时机调用 triggers，它不需要"理解" hidden 是什么意思。

### 4.4 visibleAs 为什么是固定字段而不是放在 props 里

`owner` 和 `visibleAs` 是仅有的两个固定字段，这是一个刻意的设计决策。原因是：

`owner` 决定了棋子属于谁，这是五子棋最基本的概念，胜负判定要用它，每个技能都要用它。如果放在 props 里，每段 AI 生成的代码都要写 `stone.props.get("owner")`，既啰嗦又容易出错。

`visibleAs` 决定了棋子在渲染层应该显示为什么颜色（或者不显示）。它需要渲染层直接读取，不经过任何技能代码的中转。如果把"某些棋子对某一方不可见"的逻辑全部交给 props 和技能代码去处理，渲染层就必须执行技能代码才能决定画什么，这会带来严重的耦合问题。

其余所有状态（冻结、护盾、伪装、爆炸……）不是每个技能都需要、也不需要渲染层直接感知，所以放在开放的 tags/props/triggers 里。

### 4.5 格子本身也有 tags/props/triggers

格子和棋子的开放结构是独立的。这意味着"地形效果"和"棋子效果"可以叠加。比如一个格子可以被标记为 `"cursed"`（任何落在上面的棋子 3 回合后消失），同时上面的棋子可以有 `"shielded"` tag（免疫一次负面效果）。两者的交互逻辑完全由技能代码自己处理，引擎不需要知道 cursed 和 shielded 会怎么互动。

### 4.6 全局状态也是开放的

除了格子和棋子，我们还在 GameState 上加了 `globalTags`、`globalProps`、`globalTriggers`。这是为了处理那些不属于任何具体格子的效果。比如"雾里看花"是一个全局效果（接下来几回合所有新落子对对手不可见），它不附着在某个格子或棋子上，而是改变了整个游戏的信息规则。如果没有全局状态层，这类技能就无法表达。

## 五、API 设计的六维度框架

### 5.1 为什么需要一个框架来论证"够不够"

开放式数据结构解决了"数据层够不够"的问题（答案是永远够，因为没有固定 schema）。但表达力的真正瓶颈转移到了 API 表面：**AI 生成的代码能调用哪些函数？**

如果只提供 `getCell` 和 `setCell`，AI 理论上能做任何事，但实际上会非常痛苦——每个技能都要自己写遍历逻辑、自己管理延迟效果、自己处理事件注册。代码会又长又容易出错。

所以我们需要一组设计良好的高层 API，同时需要一个框架来验证这组 API 的覆盖面是否完整。

### 5.2 六个维度

我们把五子棋棋盘上所有可能的技能效果归纳为六个维度：

**空间**：技能在哪里生效，影响多大范围。涵盖单格操作、区域操作、条件筛选、方向查找。

**实体变更**：对棋子和格子做什么修改。涵盖增（放置）、删（移除）、改（变色/加标签/改属性）、移（换位置）。

**时间**：效果什么时候生效、持续多久。涵盖立即执行、延迟 N 回合触发、每回合持续执行、到期自动清理。

**流程**：改变游戏的回合结构。涵盖追加回合、跳过回合、强制落点、修改胜利条件。

**信息**：谁能看到什么。涵盖隐藏棋子、伪装棋子、全局迷雾。

**规则**：修改胜负判定本身。涵盖改变连子数要求、排除某些连线、覆盖判定结果。

### 5.3 为什么这六个维度是"完备"的

任何一个五子棋技能，本质上都是对以下问题的回答：在哪里（空间）、做什么（实体）、什么时候（时间）、对流程有什么影响（流程）、谁知道（信息）、对规则有什么影响（规则）。

这六个维度的笛卡尔积就是所有可能技能的空间。只要每个维度都有充足的操作原语，组合出来的空间就覆盖了我们能想象到的一切技能。

我们用 12 个刻意选取的、差异极大的成语技能做了验证（偷梁换柱、暗度陈仓、围魏救赵、金蝉脱壳、天罗地网、乾坤大挪移、以逸待劳、瞒天过海、破釜沉舟、借刀杀人、釜底抽薪、石沉大海、雾里看花），每一个都能在这套 API 内完整实现。

### 5.4 唯一的硬边界

这套系统有一个真正不可扩展的地方：**事件类型列表**。

我们定义了 11 个事件时机（onTurnStart、onBeforeSkill、onSkillExecute、onAfterSkill、onBeforePlace、onAfterPlace、onStoneRemoved、onStoneTransformed、onBeforeWinCheck、onWinCheck、onTurnEnd）。如果 AI 想在一个未定义的时机触发效果（比如"当对手思考超过 10 秒时"），那确实做不到。

但棋类游戏的事件时机是有限且可穷举的。一个回合的完整生命周期就是"回合开始→技能阶段→落子阶段→移除/变换→胜负判定→回合结束"，我们的 11 个事件覆盖了每一个环节以及每个环节的"前"和"后"。

另一个边界是：如果技能需要引入五子棋之外的全新游戏机制（比如骰子、手牌、资源采集），这套 API 做不了。但这已经超出"五子棋技能"的定义范畴了，不算表达力不足。

## 六、渲染层的降级策略

### 6.1 问题

数据层可以无限开放，但前端总得知道怎么画。一颗带有 `"hidden"` tag 的棋子应该画成半透明，一个 `"blocked"` 的格子应该画个遮罩。但如果 AI 发明了一个 `"radioactive"` tag，前端不认识，怎么办？

### 6.2 解决方案

两层策略叠加：

第一层，AI 在生成技能的同时输出 `renderHints`，告诉前端这个新 tag 应该怎么显示（图标、颜色、动画）。前端维护一个 renderHints 注册表，每次新技能带来新 tag 就往里合并。

第二层，兜底降级。如果某个 tag 既没有预设渲染规则、AI 也没给 renderHint，前端统一显示一个通用标记（比如小圆点）。功能上不受影响（逻辑在代码里跑得通），只是视觉上退化。

这保证了 AI 生成任何合法技能都不会导致渲染层崩溃。

## 七、技能执行安全

### 7.1 为什么 V1 选择 new Function 而不是 Web Worker

AI 生成的代码需要在前端执行。安全隔离有两个选项：`new Function()` 传入受限上下文，或者 Web Worker 完全隔离。

V1 选择 `new Function` 的原因是：

技能代码的入参只有一个 BoardAPI 对象，它没有 `window`、`document`、`fetch` 等全局变量的引用，能做的事情被严格限定在 API 方法内。而 Web Worker 虽然隔离更强，但它与主线程通信是异步的，而我们的技能执行流程中有 `requestPlayerChoice` 这种需要等待用户交互的操作，Worker 内的异步通信会让流程控制变得非常复杂。

如果后续发现安全问题再升级到 Worker 隔离。

### 7.2 技能代码只能操作 API

这是最关键的安全约束。AI 生成的 execute 函数接收的唯一参数是 api 对象。它无法访问 GameState 的内部引用（API 方法返回的都是只读快照或深拷贝），也无法访问 DOM 或浏览器 API。所有对游戏状态的修改都必须通过 API 方法，这意味着引擎可以在每个操作上做校验、记录日志、触发事件。

## 八、能量系统的设计考量

### 8.1 为什么需要能量

如果技能没有任何使用成本，最优策略就是每回合都发动技能，普通落子永远不会被选择。这会让"五子棋"的部分完全被技能盖过。

能量系统的作用是制造取舍：你可以攒能量放一个大招，也可以频繁用小技能；有时候普通落子反而是最好的选择，因为你需要攒能量。

### 8.2 为什么是 AI 来定技能消耗

技能的消耗（cost）和冷却（cooldown）由 AI 在生成技能时一并给出。这是"运行时生成游戏机制"的一部分——不只是效果由 AI 决定，平衡性也由 AI 决定。

我们在 prompt 中给 AI 设计原则（比如"不要设计一击必杀的效果"、"cost 与效果强度匹配"），依赖 AI 的判断力来做初步平衡。V1 不做复杂的自动平衡校验，但在 Phase 5 会加入基础的兜底检查（比如 cost 为 0 但效果涉及移除对手棋子时自动拒绝）。

## 九、技能缓存策略

同一个成语在同一局游戏中只会调用 AI 生成一次，之后复用缓存的技能定义。

原因有二。第一，一致性——如果同一个成语每次生成不同的效果，玩家无法形成策略，"记住哪些成语有什么用"是策略深度的来源之一。第二，成本和延迟——每次调用 AI API 都有时间和费用开销，缓存后只有第一次使用新成语时需要等待。

但不同局之间不缓存，每局重新生成。这是为了保持新鲜感——同一个成语在不同对局中可能产生不同的技能，让每一局都有探索的乐趣。

---

## 十、总结：设计决策速查

| 决策 | 选择 | 原因 |
|------|------|------|
| 技能表达方式 | AI 生成代码（方案 C） | 表达力最高，符合实验目标 |
| 数据结构 | 开放式 tags/props/triggers | 无法预见 AI 会发明什么属性 |
| owner/visibleAs 固定 | 不放入 props | 高频使用 + 渲染层直接依赖 |
| 格子也有 tags/props | 独立于棋子 | 支持地形效果与棋子效果叠加 |
| 全局状态也开放 | globalTags/Props/Triggers | 支持非局部效果（如全局迷雾） |
| API 设计框架 | 六维度覆盖论证 | 保证表达力完备性 |
| 事件模型 | 11 个事件 | 覆盖回合完整生命周期 |
| 渲染未知 tag | renderHints + 通用降级 | AI 发明新概念时不崩溃 |
| 执行安全 | new Function + 受限上下文 | V1 够用，避免 Worker 复杂度 |
| 能量系统 | 有成本才有取舍 | 防止技能完全碾压普通落子 |
| 技能缓存 | 局内缓存，局间不缓存 | 一致性 + 新鲜感 |
